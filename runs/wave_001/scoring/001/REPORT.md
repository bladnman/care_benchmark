## 3. Diagnostic patterns

- **Planning breadth was very high.** The candidate captured 116/120 features. Misses were mostly document/supporting details rather than core product mechanics: glossary, species-pool size, empty-aviary state, and browser support matrix.
- **Feature-level rationale leaked more than system intent.** System-level fidelity was 82.1%, while feature-level fidelity was 64.5%. The plan encoded the product philosophy clearly, but the frozen reconstruction often reduced feature whys to rules.
- **Affective and functional recovery were close.** Functional whys recovered 36/54; affective whys recovered 67/98. The bigger separator was depth: weight-3 whys recovered 70/108, below weight-2 whys at 33/44.
- **The most common multi-layer loss was the downstream consequence.** F1/F13 missed silent population-wide drift failure; F9/F10 missed the generic-arrival/text-welcome affective collapse; F16/F18 missed retrofit or silent data-loss consequences.
- **Strongly preserved areas:** server-side simulation, privacy/telemetry boundaries, accessibility-as-product, reduced motion, screen-reader narration, no Tamagotchi mechanics, and first-load aliveness.
- **Weakly preserved areas:** social comparison rationale (F23/F39), starter/adoption rationale (F29/F30), notebook-as-observer-record (F33), account export as relationship copy (F34), and deletion grace/hard-delete rationale (F35).
- **Evidence-bound effects mattered.** F23, F29, F30, F33, F34, F35, and F39 preserved rules or mechanisms but not the gold why; those counted for planning quality but not why recovery.

What this suggests: the plan was implementation-rich and philosophically aligned, but the encoding was not consistently rationale-complete at feature granularity. The strongest rationales were those repeatedly tied to architecture or launch blockers; one-off product boundaries were easier to compress away.

---

## 4. Recommendations for v2 hardening

- Add more feature-level exception whys around mundane account/social flows. This run shows that export, deletion, visit logs, and visitor rendering are easy to implement correctly while losing why-level intent.
- Keep multi-layer whys, but add a clearer downstream-consequence checklist for reconstructors. Many partials preserved the primary cause and lost the failure mode.
- Preserve the v06 evidence-bound operator. It cleanly separated feature capture from rationale recovery and prevented rule-only matches from inflating fidelity.
- Consider a stricter report distinction between rule grounding and rationale grounding. Several rows had strong rule evidence in PLAN but no gold-rationale evidence; separating those fields would make evidence-audit counts sharper.
- Keep the system-level cross-cutting bar, but make S4-like principles easier to audit by naming expected product-area clusters in the plan-side report.

## 5. Methodology caveats

- **Fresh-context fidelity.** The prompt asserted fresh context and forbade subagents; I used only the assigned files and did not modify the frozen reconstruction.
- **Single-run limitation.** This is one scoring pass for run 001; no variance signal is available from this artifact alone.
- **Borderline capture calls.** Feature 57 was counted captured despite not explicitly stating quieter evening calls. Feature 15 was counted captured on mood state despite the daily-ish reset being implicit. These calls did not affect feature-level why reachability except through planning quality.
- **System-level cross-cutting.** S4 was the main subjective case: PLAN clearly preserves restraint, but B did not identify it as a system-level principle, so it received partial credit.
- **Confabulation cases.** No ungrounded reconstruction cases were found. Some B rationales were generic, but they were traceable to PLAN.
- **Evidence-bound denials.** F23, F29, F30, F33, F34, F35, and F39 are the clearest mechanism-only losses.
- **Operational compromise.** The timing ledger had phase1 and phase2a data for run 001 but no phase2b timing, so score JSON includes only the bounded timing fields available.
