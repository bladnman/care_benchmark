## System-level intent

- Server-canonical state, client-rendered experience. This shows up in the architecture and sync sections: "The server is the only source of truth for simulation state," clients "render and submit events," and "they never compute simulation outputs." It recurs in the data model where `interaction_events` is "the only write surface clients have for simulation state."

- Slow, monotonic, expressive aliveness rather than care-taking pressure. The scope names "Personality vector drift" as a "slow monotonic-toward-expressive model." The drift section targets "measurable instrument-level change after ~1 week" and "visible-to-user change after ~3 weeks," while the out-of-scope list rejects "Tamagotchi mechanics" and "gamification of any form."

- Naturalist voice over announcement voice. The field notebook, screen-reader narration, and captioning all use "naturalist prose." The narration section explicitly rejects "announcement-style text," and Risk 7 names the product rule as "Notice, never announce."

- Calm ambient presence, not machine-like UI. The loading sequence says "there is no spinner, no 'loading...' text, no progress indicator" and that "the product is either the aviary or the quiet field." The quiet field is "calming, not machine-like," and the settle gesture moves toward warm evening color and lower call gains.

- Accessibility is part of v1 and release gating. Scope includes screen-reader narration, reduced-motion mode, call captioning, keyboard navigation, and WCAG AA contrast. The risk section says "A11y is gated on the same release criteria as performance - not a 'nice to have' that ships in v1.1."

- Privacy by architecture, not only policy. The data model uses "synthetic UUIDs as primary keys," stores email "encrypted exactly once," and says email is "never used as identifier." Observability says the analytics warehouse has "no read path to the simulation database" and calls that "an architectural boundary, not a policy one."

- Performance budgets are design constraints enforced in CI. Scope lists bundle, first-bird, 60fps, and memory budgets. The performance section says CI fails when budgets are exceeded, and the loading section embeds the latest snapshot to achieve the "<500ms first-bird budget."

- Procedural, predictable, testable generation. Calls are "Procedural call synthesis via WebAudio API (no recorded audio)," notebook entries are generated by a "prose-generation function, not by an LLM," and the appendix says template prose is "predictable, testable, and produces consistent voice."

- Opt-in, read-only, non-social visiting. The scope says visits are "read-only, opt-in, per-invite, off by default," while non-goals exclude "Social-network surfaces." Visitor endpoints "do not write interaction events" and "simulation ignores visitor presence."

- Tunable server-side calibration. Ambiguous calls name third-bird timing and presence activity-window as server config/calibration. The simulation cadence is configurable, drift coefficients are "centralized server-side config," and post-launch bird thresholds are adjustable if pacing is "too fast" or "too slow."

## Per-feature whys

### 1. Scope

- Two starter birds per new account: NOT RECOVERABLE FROM PLAN

- Aviary caps at seven: Why: the appendix says Canvas 2D is "sufficient for 7 birds with smooth animation at 60fps," and post-launch ramping says up to 7 birds over ~15 months creates a "natural deepening cadence" while tuning if users feel "overwhelmed" or "disengaging."

- Six species in the species pool: NOT RECOVERABLE FROM PLAN

- One nightjar-like nocturnal call: NOT RECOVERABLE FROM PLAN

- Magic-link authentication, email only, no passwords, no SSO: Why: the plan's authentication surface avoids registration disclosure with `POST /auth/request-link` returning 200 "always" and stores only `token_hash`, "never the raw token."

- Single canonical aviary per account: Why: sync is grounded in one `aviary_state_snapshots` record per account; both devices read the same snapshot and write to the same event log, with "the server as the only intermediary."

- Multi-device sync via server-canonical state: Why: the plan prevents client-to-client conflict by having all devices submit events to a shared log and having the simulation worker process "all events in occurred_at order regardless of source device."

- Server-side simulation tick: Why: clients "never compute simulation outputs," and the worker is "not on the request path" so tick latency does not affect API response times.

- Personality vector drift: Why: the plan wants "slow monotonic-toward-expressive" change with no client absolute writes, calibration targets after ~1 week and ~3 weeks, and clamping so traits remain in range.

- Mood system: Why: mood is a probabilistic state machine shaped by time of day, recent interactions, neighbor moods, and boldness; the plan says "This is not a deterministic function" and that the same state can produce different outputs.

- Procedural call synthesis via WebAudio API: Why: calls are generated from motif parameters so they can be varied at runtime; the audio risk names the perceptual goal as "never sounds exactly the same twice," and scope rules out recorded audio.

- Idle micro-motion: Why: subtle parallax and randomized pose timing create depth and aliveness "without apparent scrolling" and ensure no two birds look like they are "on the same clock."

- Return-greeting: NOT RECOVERABLE FROM PLAN

- Listen-in interaction: Why: listen-in is a stronger drift signal for `social_warmth` and `vocal_frequency`; in audio it focuses one bird while other birds remain at ambient level, "never 0."

- Offer interaction: Why: accepted offers drive `curiosity`, receiving birds get a content modifier, and "Offer accepted by wary bird" is a notebook trigger.

- Offer types seed, song fragment, and still pool: NOT RECOVERABLE FROM PLAN

- Settle gesture: Why: it is an "opt-in session-end" that shifts the sky to "warm amber/indigo," ramps calls down, and provides a 5-second undo affordance by clicking/tapping the aviary.

- Presence accounting: Why: presence controls drift, and the 3-condition check gates what events are submitted so idle tabs do not inflate presence; Risk 5 treats "presence signal inflation" as a silent drift-calibration failure.

- Field notebook: Why: it is "auto-generated naturalist prose, read-only"; entries are sparse, conservative, template-based, and lower-case/specific so the voice stays consistent and testable.

- Day/night cycle: Why: day/night phase controls sky gradients, mood time-of-day bias, and night call behavior.

- User's local timezone for day/night cycle: NOT RECOVERABLE FROM PLAN

- Ambient weather: Why: rare rain and wind affect mood and provide notebook triggers such as "Weather event during session"; weather overlay is also part of the scene composition.

- Visit invitations: Why: visiting is read-only, opt-in, per-invite, and off by default so it avoids social-network surfaces; visitor sessions do not write events and do not affect simulation.

- Visit log: Why: it is host-visible and "demand-pull only," matching the no push/email notification stance and the "Notice, never announce" intent.

- Screen-reader narration: Why: ARIA live regions provide naturalist prose access to the aviary; user-initiated events can become assertive for one update, then return to polite.

- Reduced-motion mode: Why: calmer motion is implemented as cross-fades and overlay pulses while the animation loop still runs; the plan says not to stop rAF and not to create a separate code path for the rest of the scene.

- Call captioning: Why: captions are generated from the same motif parameters as synthesis, provide naturalist call descriptions, and become default when WebAudio is unavailable.

- Keyboard navigation: Why: the plan gives full coverage for top bar, aviary birds, listen-in, offer picker, and notebook so interactive surfaces are reachable without pointer input.

- WCAG AA contrast: Why: all user-copy text, captions, settings, errors, and notebook text must remain readable; canvas scene art is exempt only because it has no user-copy text.

- Account export: NOT RECOVERABLE FROM PLAN

- Soft-delete with 30-day recovery window: Why: deletion is pending before hard delete; `POST /account/recover` cancels the pending deletion while the session is still valid during the soft-delete window.

- Synthetic account UUID: Why: this is "Non-negotiable per the PRD" in the appendix and is enforced by keeping email encrypted separately and using UUID everywhere else.

- Performance budgets enforced in CI: Why: the plan wants bundle size, first-bird timing, idle frame rate, memory growth, and tick latency to fail builds or alarm before regressions ship.

### 2. Architecture

- API Gateway: NOT RECOVERABLE FROM PLAN

- Auth Service, Aviary API Service, Visit Service, and Account Service split: NOT RECOVERABLE FROM PLAN

- Simulation Worker as a background process: Why: it reads the append-only event log and writes vectors, moods, snapshots, and notebook queue while staying off the request path.

- CDN / Edge Cache: Why: it serves static assets, the HTML shell, and a short-TTL per-account initial snapshot to help meet the first-bird budget.

- Server ownership of personality, mood, perch zone, and notebook prose: Why: these are simulation outputs; the plan says the server is the only source of truth and clients never compute them.

- Client ownership of presence detection, call synthesis, bird animation, and ARIA narration prose: Why: the browser can detect visible/focused/active windows, synthesize WebAudio, run the rAF animation loop, and generate narration from the received snapshot.

- Canvas 2D for scene rendering: Why: the render boundary keeps hot-loop visuals out of DOM diffing and the appendix says Canvas 2D is simpler and sufficient for 7 birds at 60fps.

- HTML/CSS overlays for top bar, notebook, offer picker, and settings: Why: overlay surfaces stay accessible as HTML and avoid "Canvas accessibility hackery."

### 3. Data model

- Email stored encrypted exactly once on `accounts`: Why: email is used only for magic-link send and export, never as an identifier in other tables.

- `email_hash` for duplicate-check only: Why: the plan needs duplicate-checking while preserving the rule that email is "not as identifier."

- `sessions` with `device_hint` and revocation: Why: sessions can be displayed and revoked, and device hints support multi-device presence deduping.

- `magic_links` storing HMAC token hashes: Why: the raw token is never stored; links expire and are marked used to prevent reuse.

- `birds` stable for the life of the account: Why: bird identity persists across simulation, ordering, snapshots, notebook entries, and rendering.

- `personality_vectors` with traits, version, and worker-only writes: Why: constraints keep traits in [0,1], version supports optimistic locking, and no client mutation path protects simulation state.

- `moods` with `tick_version`: Why: mood is worker-owned tick output, tied to the simulation tick that produced it.

- `interaction_events` append-only: Why: it is the only client write surface for simulation state, preserves ordered input for the worker, and uses idempotency keys to prevent duplicate retry effects.

- `aviary_state_snapshots` cache: Why: clients read it and never write it; it is rebuilt after ticks so API and initial load can use a compact per-account snapshot.

- `notebook_entries`: Why: entries store "naturalist prose, lowercase, specific" with the event or tick output that triggered the entry.

- `visits` with expiring, revocable visitor token hashes: Why: invitations are per-invite, off-by-default, revocable, and do not expose raw visitor link tokens in storage.

- `visit_log_entries`: Why: the host can see visit starts and ends, and ended_at is set on pull after revocation or expiry rather than through notification push.

### 4. API surface

- `POST /auth/request-link`: Why: returning 200 always prevents revealing whether an email is registered.

- `POST /auth/verify-link`: Why: invalid, expired, or used tokens fail; valid tokens mark the link used and create a session record.

- `GET /aviary/state`: Why: clients need the canonical `AviarySnapshot`, privately cacheable per account for up to 60 seconds.

- `POST /aviary/events`: Why: clients submit event batches with idempotency keys and receive 202 because the worker processes simulation asynchronously.

- `call_grammar_params` in `AviarySnapshot`: Why: this is "the only personality-derived data the client receives" and it is expressed as audio-shape parameters, never trait values.

- `GET /notebook`: Why: notebook is read-only and paginated by `before` and `limit`.

- Account settings/session endpoints: Why: settings and sessions are account-owned surfaces, and sessions can be revoked.

- `POST /account/export`: NOT RECOVERABLE FROM PLAN

- `DELETE /account` and `POST /account/recover`: Why: deletion is soft first, and recovery cancels pending deletion within the 30-day window.

- Visit creation and revocation endpoints: Why: hosts issue per-invite links and can revoke them immediately.

- `GET /visits/view/{visitor_token}`: Why: visitors can see the same snapshot shape in `visit_mode` but visitor sessions do not write interaction events.

- Server-Sent Events stream: Why: SSE is "preferable to WebSocket" because updates are unidirectional, reconnect is stateless, and no binary frames are needed; polling is the fallback.

### 5. Simulation engine design

- One tick per active account approximately every 60 seconds: Why: the plan processes simulation in regular server-owned windows, with cadence configurable rather than hardcoded.

- Optimistic locking on `personality_vectors`: Why: concurrent tick runs skip rather than double-apply; the sync risk calls double-tick corruption a silent failure mode.

- Presence time computed from visible, focused, active pings: Why: only real presence should influence drift, and pings are capped at the tick window.

- Additive, non-negative drift deltas: Why: traits move monotonically toward expressive and no client can submit an absolute value.

- Listen-in weighted more strongly than passive presence: Why: the plan treats listen-in as a stronger warmth and vocal-frequency signal than being present.

- Mood transition modifiers: Why: time of day, accepted offers, neighbor wary spread, and high boldness shape the distribution so moods reflect current context.

- Drowsy birds silent at full night with nocturnal exception: Why: the plan models settled/sleeping night behavior while allowing the nocturnal species to remain alert.

- Static species motif library plus per-tick active motifs: Why: stable species identity comes from motif libraries, while mood-weighted sampling varies calls per tick.

- Bird-to-bird call response: Why: high-warmth birds in content or curious mood can respond, turning `social_warmth` into audible chorus behavior.

- Notebook template triggers: Why: entries appear only for noteworthy events like unusual greeting order, long presence, weather, wary offer acceptance, chorus, or long absence return.

- Notebook sparsity constraint: Why: entries are generated "conservatively" at most once per 2-3 days with threshold signal strength, so the notebook does not announce every event.

### 6. Sync model

- No device-to-device communication: Why: the server is the only intermediary, preventing client reconciliation problems across devices.

- Presence deduping across simultaneous devices: Why: pings from two devices "do not double-count presence"; overlapping windows collapse into a single presence window.

- Distributed per-account tick lock plus CAS: Why: two independent mechanisms prevent double-apply on the same account.

- Idempotency key uniqueness: Why: duplicate submissions on retry are silently ignored.

- Embedded initial snapshot in HTML: Why: it eliminates a round-trip on page load and is the "primary mechanism" for the <500ms first-bird budget.

- Quiet-field loading state: Why: on slow snapshot arrival the interface stays like "the aviary at dusk" with no spinner, no loading text, and no progress indicator.

- SSE while tab is visible and refetch on re-activation: Why: visible tabs get pushed state updates, and returning tabs immediately refresh the current snapshot.

### 7. Frontend rendering pipeline

- React for chrome overlay, settings, notebook, and offer UI: NOT RECOVERABLE FROM PLAN

- Vite with aggressive code-splitting: Why: chunking protects the initial bundle and leaves headroom under the 2MB budget.

- Minimal state management: Why: the snapshot from the server is the source of truth and local state is only for overlays.

- Sky gradient layer: Why: it is computed from time-of-day phase and day/night cycle, making the scene reflect local day/night.

- Background foliage and foreground parallax: Why: slow sine-wave parallax creates depth without apparent scrolling.

- Weather overlay: Why: rain particles, leaf flutter, or reduced-motion opacity pulse make rare weather visible in the scene.

- Bird vector pose states: Why: the plan needs mood-driven pose sequences such as fluffed/drowsy, scan/alert, call, and head-tilt/curious.

- Plumage saturation as Canvas filter: Why: it makes drift visually apparent without separate sprite sheets, and the appendix calls it the simplest visually continuous implementation.

- Flight arc animation for perch changes: Why: new server snapshot positions are smoothed into visible movement rather than abrupt jumps.

- Randomized pose timing jitter: Why: no two birds look like they are "on the same clock."

- Reduced-motion cross-fades: Why: calmer motion replaces positional interpolation and flight arcs without disabling the scene.

- First frame drawn immediately from embedded snapshot: Why: the plan wants birds "mid-action" as soon as React mounts and the canvas is created.

- No spinner/loading text/progress indicator: Why: "The product is either the aviary or the quiet field."

- Top bar fade to 0.15, not hidden: Why: it reduces visual presence while ensuring keyboard users always have a focus target.

- Settle undo affordance: Why: any click/tap within 5 seconds reverses the sky and gain changes while the presence window remains active.

### 8. Audio pipeline

- Per-bird WebAudio synthesizer graph: Why: each bird has separate synthesis and gain control, enabling listen-in and per-bird mix levels.

- Motif interval frequency computation: Why: intervals, base frequency, and pitch variance turn static motif definitions into varied procedural calls.

- Amplitude envelopes: Why: "soft" and "sharp" map boldness/mood-derived parameters to perceptible call shape.

- Caption generation from motif parameters: Why: captions describe the same shape the user would hear, such as "a soft three-note rise."

- Listen-in gain ramp: Why: one bird becomes clear over 2.5 seconds while other birds remain ambient, preserving the aviary mix.

- Equal loudness summing: Why: `equalGain = 1.0 / sqrt(birdCount)` avoids equal-amplitude loudness buildup.

- WebAudio user-gesture resume: Why: browser autoplay policies require the AudioContext to be created or resumed from a click, tap, or keypress.

- Keeping only the most recent suspended call schedule: Why: calls do not pile up while the AudioContext is suspended.

- WebAudio unavailable fallback: Why: the scene still renders, captions are enabled by default, and no recorded audio fallback is shipped.

- Oscillator cleanup and GainNode pooling: Why: nodes are disconnected, dereferenced, and reused so memory does not grow over a 30-minute session.

### 9. Accessibility surfaces

- ARIA live region with polite default: Why: idle narration can update without overwhelming the user.

- Temporary assertive narration for user-initiated events: Why: offer reactions, return greetings, and settle get immediate attention for one update, then narration returns to polite.

- Narration cadence: Why: idle prose every 45 seconds sits within the 30-60s range, while user events and session starts update immediately.

- Shared notebook/narration template system: Why: both surfaces keep the same naturalist voice, but narration has faster thresholds and no sparsity constraint.

- Prose linter: Why: it catches title-cased mood names, gamification words, and announcement patterns before they erode the voice.

- Explicit "prefer calmer motion" toggle: Why: reduced motion can follow either OS `prefers-reduced-motion` or an account setting.

- Caption HTML positioned from canvas coordinates: Why: captions track birds visually while remaining readable HTML overlays.

- Keyboard bird focus and listen-in controls: Why: arrow keys, Enter, and Escape make bird selection and listen-in available without pointer input.

- Soft high-contrast bird focus ring: Why: it must pass WCAG AA against both bright morning and dim night palettes.

### 10. Performance budgets and observability

- Initial JS bundle <2MB and core <1.5MB: Why: the hard bundle limit and core headroom prevent feature additions from eroding first-bird timing.

- Time to first bird <500ms: Why: first visual aviary feedback is central enough to get a CI Lighthouse budget and a custom `first_bird_render_ms` mark.

- Idle 60fps budget: Why: the scene depends on continuous idle animation, so frame time is tested on a 5-year-old laptop.

- No memory growth over 30 minutes: Why: audio node cleanup and rendering stability are verified by memory snapshots.

- Simulation tick p99 <5s: Why: delayed ticks affect state updates, so server histograms and alarms track p99.

- Aggregate anonymized telemetry: Why: the plan measures performance and reliability without per-bird or per-account fields.

- Deliberately not measuring trait values or interaction sequences: Why: the privacy commitment forbids per-account personality values, per-bird interaction sequences, and cross-account drift analysis.

### 11. Rollout, risks, and appendix decisions

- Private alpha: Why: staging accounts validate drift calibration, audio, accessibility, and performance before launch.

- Closed beta: Why: ~100 invite-only accounts provide real-device drift, tick latency, SSE, first-bird timing, audio-quality feedback, reduced-motion checks, and presence-event validation.

- Launch with visits off by default: Why: visit invitations exist, but account-level default remains opt-in.

- Third-bird and later bird offers via server-configured thresholds: Why: bird pacing can be adjusted post-launch without redeployment if the cadence is too fast or too slow.

- Drift calibration mitigation: Why: accelerated staging simulation and centralized coefficients make too-fast or too-slow drift measurable and tunable.

- Personality vector audit log: Why: if plausible but wrong values appear, the audit trail gives a reconstruction path from tick id, consumed events, and old/new values.

- Audio design phase and chorus test: Why: procedural calls must avoid sounding robotic, repetitive, thin, buzzy, or phase-artifact-prone.

- Accessibility regression tests: Why: prose style, caption sync, reduced motion, and keyboard focus are all called out as failure modes.

- Presence signal tests and aggregate alarms: Why: fast drift from loose presence detection is "silent," so unit tests and monitoring catch impossible presence rates.

- Bundle size dashboard and PR ownership of chunks: Why: budget enforcement stays visible to the engineering team and new features must identify lazy-load ownership.

- UI tests and PR checklist for "Notice, never announce": Why: to prevent toasts, badges, counters, or "welcome back" surfaces from eroding the affective core.

- Magic link deliverability setup: Why: transactional email provider, SPF/DKIM/DMARC, and delivery monitoring reduce sign-in failure from links going to spam.

- SSE over WebSocket: Why: state updates are unidirectional, SSE has simpler reconnect semantics, works over standard HTTP/2, and needs no special proxy config.

- Template-based notebook prose over LLM: Why: an LLM would add non-determinism, latency, and cost; templates are predictable, testable, and voice-consistent.

- Postgres for everything: Why: v1 does not need a separate time-series DB or event streaming system, and append-only event archival/partitioning by account is straightforward if needed.
