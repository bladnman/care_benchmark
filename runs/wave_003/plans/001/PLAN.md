# Pocket Aviary v1 implementation plan

## 1. Scope and product contracts

Build a web-only, single-user-per-account aviary: one canonical aviary, two starter birds, and age-paced additions up to seven. Ship email magic-link authentication, multi-device snapshots, server-owned simulation, presence accounting, offers, listen-in, settle, the read-only field notebook, and optional per-invite read-only visits. Ship screen-reader narration, a designed reduced-motion surface, call captions, keyboard access, and WCAG AA contrast at launch.

The core user experience is a single horizontal, one-screen scene that appears already in motion. Birds greet without textual welcome, respond to attention and offers, and accumulate slow, monotonic personality drift. The product uses naturalist, lowercase, present-tense copy on bird-facing surfaces; sign-in, account, settings, accessibility-settings, and error surfaces use clear matter-of-fact copy.

Keep explicit v1 non-goals out of the architecture and UI: native apps, payments, multiple aviaries, shared aviaries, customizable scenes, profiles, follows, public discovery, feeds, comments, chat, co-presence, leaderboards, scores, achievements, streaks, visit-frequency displays, hunger, death, distress, push notifications, and gamified progression. Do not expose personality values in product UI. The user may download a state export from account settings, which includes the specified current vectors; this is an export, not a stats surface. Visits are opt-in per invite and read-only. Any visit notification preference is explicitly off by default and never appears in onboarding.

Treat these as acceptance contracts, not styling suggestions: birds never punish absence; tab close and settle both end presence; clients never advance simulation; the server is the sole writer of canonical vectors; and a visitor cannot influence host state.

## 2. Architecture and ownership boundaries

Use a browser client, an authenticated application/API layer, a durable per-account simulation store, and background tick workers. Split account/auth, aviary state and event ingestion, simulation, notebook, and visit authorization into modules or services according to the deployment scale; keep one canonical transaction boundary for aviary state. A relational store is a practical default because account ownership, ordered append-only events, snapshots, invitations, and deletion need durable transactions and constraints. Queue or lease due aviaries to tick workers; make tick execution safe to retry. Do not build client-to-client replication.

The server owns account identity, bird identities, names, species, personality vectors, moods, simulation timestamps, pending transitions, interaction event ordering, notebook entries, and invitation/revocation status. The client owns only ephemeral presentation state: current interpolation, focus, open panels, listen-in selection, local audio nodes, and render-only ornaments. Client state is discarded or reconciled from a fresh snapshot after visibility return or suspension.

Render boundary: the simulation API returns a compact render snapshot with stable IDs, render-ready perches/poses, mood-derived presentation cues, call timing/motif identifiers, day/night/weather state, and active transition timing. It does not send numeric personality traits to normal clients. Rendering maps snapshot values to SVG/canvas scene assets and pose transitions; no product view can inspect or serialize hidden vectors. Keep scene drawing independent from API and audio implementations so all can consume the same snapshot.

Use server UTC timestamps for ordering, expiration, and durable history; retain the account's IANA time zone for local day/night and daily mood timing. Clients can provide their current zone during onboarding/settings, but never use client wall-clock time to author canonical progression. Resolve ambiguous local-time boundaries deterministically and test daylight-saving changes.

## 3. Data model

All foreign keys and telemetry references use a random synthetic account UUID. Store email encrypted only on its account/auth record; do not derive identifiers, logs, partition keys, or analytics dimensions from email.

- **Account**: UUID, encrypted verified email, lifecycle/deletion timestamps, IANA time zone, settings (audio, captions, reduced-motion override, opt-in visit notification toggle), creation time, schema version.
- **Device session**: opaque revocable token hash, account UUID, created/last-used/revoked timestamps and limited device label. Magic-link token hashes expire in 15 minutes and become invalid atomically on use; rate-limit requests by email without placing raw email in logs.
- **Aviary**: account UUID (unique), canonical revision, tick cursor/last tick time, last owner-presence time, settled/session presentation state, local environment state (day phase/weather and seeded transition), creation time.
- **Bird**: immutable UUID, aviary UUID, species key, renameable display name, creation/age eligibility time, server-only normalized personality vector (boldness, social warmth, vocal frequency, plumage saturation, curiosity), mood enum and mood timing, current/next perch, pose/transition, call-grammar seed/signature and next call schedule, last offer time per bird. Enforce no more than seven and stable identity across renames/migrations.
- **Interaction event**: append-only UUID, account/aviary/bird references as applicable, monotonic per-aviary sequence, idempotency key, type, server-received time, bounded payload and processing status. Types cover presence interval/ping, listen-in start/end, offer and outcome, settle/undo, and other owner session events needed by the simulator. Never accept personality deltas or absolute vectors from a client.
- **Notebook entry**: stable UUID, aviary UUID, observation time, naturalist text plus structured source facts/template version, deduplication key, creation time. Read-only to clients; sparse (roughly every few days for regular use, with noteworthy exceptions), never a raw event log or user-frequency record.
- **Invitation and visit**: invite UUID, host account UUID, encrypted/minimized invitee email, hash of one-time secret, created/expiry (30 days), revoked/used timestamps, status. Visit sessions reference invite and host IDs, track approximate start/end duration for the host's settings log, and have no simulation event capability. Revocation is checked at each snapshot pull.
- **Snapshot/revision**: canonical revision and event/tick cursor allow consistent pulls and retry detection. Store recovery/checkpoint state with the canonical aviary so vector history is never reconstructed by clients or dependent on lossy analytics logs.

The 30-day account deletion window marks the account inaccessible/marked for deletion immediately, permits signed-in recovery, then hard deletes aviary data, vectors, notebook, visits, and associated telemetry at expiry. Keep service backups on a documented purge horizon compatible with the deletion promise.

## 4. API surface and flows

Use authenticated HTTPS endpoints (or equivalent typed RPC) with strict account scoping, schema validation, idempotency, and versioned response contracts. Example surface:

- `POST /auth/magic-links` requests a link; `POST /auth/sessions` consumes it once and issues a per-device session; `GET/DELETE /account/sessions` lists/revokes sessions; account endpoints verify email changes, export, recover deletion, and initiate deletion.
- `GET /aviary/snapshot?after_revision=…` returns the compact canonical render snapshot, server timestamp, revision, own-client permissions and any active transition. A normal owner snapshot includes notebook cursor as needed, never vector numbers. Pull on initial navigation, visibility restoration, long frame gap/resume, and low-frequency visible keepalive. Use conditional responses when unchanged.
- `POST /aviary/events` accepts a batch of bounded, typed client events with unique idempotency keys and client sequence/context. Server assigns canonical sequence/time, validates ownership and cooldown, deduplicates retries, and returns accepted/rejected status. The tick consumes accepted events in order. Presence packets represent intervals only when the client currently satisfies all three required signals; server caps interval length and rejects stale/future/replayed times. Client cannot self-report arbitrary hours.
- `GET /notebook?cursor=…` returns paginated, immutable observations, with no interaction history or visit-frequency surface.
- `POST /visits/invitations`, `GET /visits/invitations`, `DELETE /visits/invitations/{id}` manage named opt-in invitations and revocation. Visitor consumes the one-time link through a separate exchange endpoint, obtaining a short-lived read-only visit token. `GET /visits/{token}/snapshot` returns the same current aviary rendering state but omits owner controls and notebook/settings; it records only visit start/approximate duration, never owner presence or interaction events. Check invite expiry/revocation on every pull; return the matter-of-fact unavailable surface immediately on the next pull. Host settings expose the ordered visit log, outstanding invitations, and optional off-by-default notification setting.

Offer submission references seed, library song fragment, or still pool and intended bird/aviary; do not trigger by clicking a bird. Enforce per-bird cooldown server-side (few minutes, calibrated) and return the reaction chosen from canonical mood/personality. Listen-in is a client audio mix choice but start/end events can be recorded as attention inputs. Settle is an event that changes scene lighting/call behavior for the session and closes presence; any scene click within five seconds sends an idempotent undo and resumes. Tab close ends presence by timeout; no required goodbye or penalty.

## 5. Simulation engine and calibration

Run a deterministic, idempotent tick approximately once per minute per aviary whether or not a client is open. Use a lease or row-level lock on the aviary revision; atomically read events after the consumed cursor, compute state, append notebook observations when warranted, update the canonical state/revision, and advance the cursor. A retry against the same cursor must yield the same result. Catch-up after downtime must use bounded elapsed-time steps or closed-form transitions so a week-old aviary does not require a burst of unbounded minute jobs.

Presence collection requires the conjunction of visible document, focused window, and pointer movement or keypress within a calibrated few-minute activity window. Use modest periodic pings with server-issued time/sequence; close the interval on hidden, blur, settle, unload when possible, and otherwise expire it server-side. The server clips gaps and overlapping device presence, and uses the documented rule for simultaneous devices (count owner attention once, with event source attribution only for processing). A visitor never contributes presence. Calibrate the inactivity window toward allowing quiet watching without counting unattended open tabs.

Drift is a low-pass filter over presence and interaction signals, weighted primarily by valid owner presence. Positive presence moves traits slowly toward expressive; no trait moves downward because of neglect. Listen-in chiefly influences the focused bird's social warmth and vocal frequency; an accepted offer nudges curiosity and making an offer near a bird nudges boldness. Settle quiets current mood and ends presence without drift. Apply bounded nonnegative deltas to stored vectors in event order, saturate at defined trait ceilings, and never compute them from client state or reconstruct from analytics. Select filter constants and normalization ranges in the simulation service, then calibrate with deterministic fixtures: measurable instrument-level movement after about a week of regular presence, no visibly attributable per-session change, and perceivable but subtle expression by about three weeks. Verify no-attention periods do not decrease vectors or generate distress.

Mood is a distinct, persistent enum (wary, content, curious, drowsy, alert; finalize the set at implementation). Transition via a seeded, deterministic state machine using recent owner interactions, user's local time, transient weather, other-bird calls/alarm response, and personality biases. Persist mood and timers across sessions; continue transitions while offline and avoid a default-mood snap on open. Evening and rain dampen calls; boldness tempers wary transitions. Birds can respond to one another, with wary influence and chorus emergence, without making them independent NPC UI states. Local time drives gradual morning/day/evening/night palette and mood. Most birds settle at night; the designated nightjar-like species may remain active. Rare brief rain a few times weekly and occasional soft wind create small mood changes, not dramatic events.

Represent each call as a procedural grammar over a small species motif library: motif choice, note contour, timing, pitch range, duration, and controlled variation derive from stable bird identity/species with bounded personality/mood modulation. Preserve a recognizable signature through mood and drift. A seeded schedule drives variable calls when unobserved and chorus participation according to vocal frequency. Caption generation must use the exact generated motif/timing and produce a short naturalist phrase for that actual call. Return motif/timing tokens in snapshots; synthesize sound on client, never download audio loops.

Greeting selection runs on owner return: choose one likely greeter from boldness/mood and absence duration, use varied gaze/step/call actions, and stagger any additional greeting by a randomized small seeded offset. Quick absences yield a glance; long absences may yield re-orientation. No textual welcome and no synchronized greeting cue.

Notebook generation is a separate rule layer over noteworthy canonical facts, not a copy of events. Use deduplication and a per-aviary sparsity budget so frequent visits do not create a feed. Facts can describe bird-specific greeting order, posture/weather/calls or quiet stretches; prohibit user visit frequency, streak language, vector values, generic event-log phrasing, and claims unsupported by state. Keep text lowercase, present-tense, specific; use vetted templates initially and version them.

## 6. Frontend scene and interaction pipeline

Compose the page as a thin top bar and a full single-screen responsive scene. Keep account/settings, accessibility settings, notebook, and offer in the top bar only; no buttons, badges, labels, tooltips, or overlays within the scene. Fade the bar toward transparency after cursor stillness and restore on pointer or keyboard activity. Match calm blues, greens, browns and ochres; apply WCAG AA to all copy and focus outlines against bright and dim scenes.

Render all birds and three front/middle/back perch zones in frame at every supported viewport. Mood/personality determine perch choice, pose, and motion; users cannot drag/place birds. Use a first-paint path that can draw the quiet field, then immediately render a snapshot with current pose/transition and ambient time phase so motion is already in progress—no spinner, fade-from-static, or wake-up sequence. The first bird target is under 500 ms on mid-tier mobile over 4G. If state is delayed, show the quiet field with faint ambient cues. A true new aviary may briefly show the quiet empty state and then the two starter birds enter softly after naming.

Use a render loop with bounded state, stable scene objects, reusable buffers, and interpolation from snapshot N to N+1. Pause client rendering and audio scheduling while hidden to save battery; server simulation continues. Pull a fresh snapshot on visibility return or long frame gap, then interpolate rather than teleport. Keep ambient leaf/feather drift and subtle parallax client-side ornaments, independent of tick and not persisted. Avoid unnecessary allocation each frame; cap updates and dispose notebook rows/audio nodes as they leave use.

Idle motion includes mood-keyed preening, scanning, head tilts, and weight shifts, continuous from the viewer's perspective. Birds and ambient activity should never read as paused. In reduced-motion mode, render designed slow cross-fades among still poses, replace flight paths with perch cross-fades, remove drifting leaves, and slow ambient color shifts while preserving calls, captions, mood, and drift. Honor OS preference initially and allow a settings override.

Interaction behavior: mouse/touch/keyboard focus starts listen-in; clicking/tapping focused bird again, another bird, empty space, or moving keyboard focus away disengages. Smoothly raise the focused bird and lower others to ambient, never silence others. The offer top-bar flow is keyboard navigable and presents the three offer types; reactions are mood/personality dependent and offers have functional few-minute per-bird cooldown. Settle transitions to evening over seconds, quiets calls, remains until active re-engagement, and supports a five-second scene-click undo. Notebook is behind its icon, scrollable indefinitely, read-only, and uses paginated fetch.

Keyboard: Tab through top bar; entering scene focuses first bird; arrows move among birds; Enter listens in; Escape exits listen-in; offer flow, settings, notebook and settle are fully reachable. Provide visible, high-contrast focus. Avoid hover-only affordances and ensure pointer and touch targets work on narrow screens.

## 7. Audio pipeline

Build calls with WebAudio oscillators/noise/envelopes and a small reusable motif library, with controlled per-call variation. Separate per-bird gain nodes feed a master/ambient mix; listen-in ramps gains gradually and leaves all non-focused birds audible at ambient level. Chorus timing comes from multiple live generated calls, never stacked recorded loops. Reuse nodes/buffers where possible, bound concurrent voices, schedule only near-future audio, and stop/dispose on hidden state, unmount, account/session changes, or revoked visit. Respect browser audio-activation policy: create/resume context after the user's first permitted gesture without delaying first visual bird.

Offer song fragments are a small library of procedural or compact motif instructions played softly through the same pipeline. Settle and night/weather influence call scheduling and mix. When captions are enabled, display short prose near the calling bird and fade it with the sound; derive it from the generated grammar, not a fixed per-bird caption. Captions remain available with audio disabled.

If WebAudio is missing or denied, use graceful silence and enable captions by default; do not ship recorded fallback audio. Bound contexts and avoid per-call leaks. Report aggregate audio-context errors only, with no bird/account state in operational telemetry.

## 8. Accessibility and voice

Provide a semantic scene region and a screen-reader running narration generated from the same canonical/render state. Narrate naturalist prose, not coordinates, trait values, or a list of status labels. At idle, update roughly every 30–60 seconds; prioritize user-triggered greeting, offer reaction, and settle observations without flooding the announcement queue. Make prose updates atomic and interruptible only where appropriate. Keep notebook and narration voice consistent.

Support reduced-motion as a designed alternate renderer, not animation removal. Offer opt-in captions for calls and enable them by default when WebAudio is unavailable/denied. Ensure all controls have clear accessible names in conventional system voice where they are settings/actions; bird-facing prose stays naturalist. Meet WCAG AA contrast for all user copy, including captions, narration if visually shown, top bar and system errors. Provide visible focus styles in all day/night states, keyboard operation throughout, and test screen-reader announcement cadence and queue behavior.

## 9. Privacy, security, and correctness

Enforce account ownership at every owner API query. Hash one-time auth and visit secrets; consume magic links atomically; expire links at 15 minutes and invitations at 30 days; revoke device sessions; verify new email before changing it. Protect event ingestion against retries, spoofed intervals, oversized batches, stale timestamps, cooldown bypass, and cross-account bird IDs. Visitor tokens authorize only read-only snapshot access, are short-lived, and are rechecked against revocation at every pull. Visitors never see controls, notebook, account settings, or contribute interaction/presence.

Use the synthetic UUID everywhere outside the encrypted email record. Keep event and canonical simulation storage inaccessible to analytics ingestion. Operational telemetry is aggregate only: request counts/latencies, tick duration/latency, errors, anonymized session-duration histograms, first-bird and render-frame timing, and audio errors. Never emit per-bird traits, moods, interactions, per-account identifiers, emails, or content to analytics/model-training pipelines. Make notebook content and visit records part of deletion/export scope as specified. State export is generated on demand and delivered to verified email by expiring download link.

## 10. Performance budgets and observability

Set release gates at: initial JavaScript under 2 MB gzipped; first bird visible under 500 ms on a mid-tier mobile device over 4G; 60 fps idle motion on a five-year-old mid-range laptop; and no client memory growth over a 30-minute session. Keep snapshots in the kilobyte range and serve initial HTML/snapshot efficiently, optionally from an edge cache only when authorization and freshness rules preserve canonical state. Lazy-load settings, accessibility settings, invitations, and notebook code where doing so does not delay the primary scene. Build compact SVG/procedural assets and split code by route/surface.

Run synthetic browser performance checks from common geographies and aggregate-only RUM. Measure navigation/first-bird timings, frame-time distribution, memory trend, request and snapshot latency, tick latency, audio-context failures, auth/visit errors, and accessibility/performance release checks. Alarm on simulation tick latency p99 above five seconds. Include canary health and queue lag. Do not use per-account simulation records for product analytics or population-level behavior reports.

## 11. Rollout and delivery sequence

1. Establish data ownership, schema/versioning, account UUID discipline, event ordering/idempotency, privacy boundaries, deletion semantics, and deterministic simulation fixtures before client behaviors depend on them.
2. Deliver magic-link auth and the server-authoritative two-bird aviary with canonical snapshots, durable one-minute ticks, local-time mood/day cycle, and starter naming. Verify stable bird IDs, canonical vector persistence, offline continuity, and no client writes to state.
3. Build the responsive scene, first-frame path, mood/perch/pose renderer, idle micro-motion, visibility/resume handling, and reduced-motion rendering. Measure bundle, first bird, frame rate, and memory early.
4. Add procedural call grammars and chorus mixer, captions/narration, listen-in, offers, settle/undo, and precise presence event capture. Calibrate drift and cooldowns with fixtures against the one-week/three-week targets and absence invariants.
5. Add sparse field notebook, on-demand export/deletion/account settings, then isolated invitation/visitor read-only tokens, revocation, expiry, visit log, and optional off-by-default visit-notification preference. Confirm no visit influences host simulation.
6. Complete keyboard/screen-reader/contrast review, browser support checks for the last two major Chrome/Safari/Firefox/Edge versions, security/privacy review, synthetic RUM dashboards, and canary rollout.

Launch with two birds per aviary. Gate age-based additions behind server rules that gradually offer birds over aviary age (for example, a third after a few months, then progressively slower additions); exact schedule is a calibration parameter, not a visit reward. Enforce seven as a hard invariant in service and database. Monitor aggregate capacity, call recognizability feedback gathered through qualitative research, p99 tick latency, render and audio health, and drift calibration through deterministic internal fixtures. Do not instrument per-account behavior or surface bird counts/progression as gamification.

## 12. Risks and mitigations

- **Drift too fast, slow, or misleading**: user-level trust erodes even if numerical tests pass. Keep coefficients versioned and adjustable; use deterministic simulated attendance traces for one-week and three-week calibration; inspect only test fixtures and aggregate operational health, not private interaction analytics. Ensure omission never subtracts traits.
- **Presence overcount or undercount**: background tabs can inflate drift, while an overly short idle timeout misses quiet watching. Enforce the three-signal conjunction on the client and server-clipped intervals; calibrate the few-minute window; test hidden, blur, sleep/wake, keyboard-only, and multiple-device cases; count concurrent owner attention once.
- **Lost or duplicated interactions across devices**: event idempotency, per-aviary sequence, transactional cursor and tick commit prevent double-application and last-write-wins vector loss. Exercise retry/crash/replay fixtures and preserve recovery checkpoints.
- **Mood or offline catch-up snaps**: persist moods and transition timers and use bounded elapsed-time advancement with stable seeds; validate local-time/DST changes and long absences. Absence yields quieter ambience only, never distress.
- **Calls sound synthetic, repetitive, or lose identity**: constrain motif variation so the signature remains recognizable, mix with headroom, avoid simultaneous greeting cues, and iterate with qualitative listening across the seven-bird ceiling. Do not solve repetition by adding looped recordings.
- **Audio policy/browser failures**: decouple visuals from audio initialization; handle gesture gating and unavailable contexts with silence and captions; exercise supported browser versions and device limits.
- **Snapshot/render mismatch or slow first frame**: draw scene shell immediately, use a compact render snapshot, include current transition timing, and refresh after visibility/suspension. Track synthetic first-bird timings and keep the initial bundle under budget.
- **Accessibility regressions from animation/copy changes**: treat narration, caption grammar, reduced-motion cross-fades, keyboard focus, and contrast as release criteria for the primary feature set; review with assistive technology and reduced-motion settings each release.
- **Privacy boundary drift**: enforce email-only-at-account-record, UUID references, isolated analytics schemas, explicit visitor capabilities, and deletion coverage in code-level ownership boundaries. Review telemetry fields and invitation revocation on every release.
- **Notebook becomes a feed or engagement mechanism**: apply sparsity budgets and template/content rules that describe birds and aviary moments only; reject visit-frequency, streak, generic event, and raw metric entries.
- **Scope expands toward game/social mechanics**: keep non-goals in acceptance review and data/API surface; do not create unused ranking, visit frequency, public profile, or achievement metrics “for later.”

## 13. Definition of ready-to-ship

V1 is ready when two starter birds render in an already-active scene across supported browsers; the server alone advances persistent identity, vectors, mood and calls; regular owner presence calibrates to measurable one-week and perceptible three-week drift without session-visible jumps; absence never harms birds; calls are procedural and individually recognizable with a functional chorus and graceful silence/caption fallback; all required interactions and sparse notebook work; multiple devices show one canonical aviary; visits are explicitly invited, read-only, revocable, expiring, and simulation-neutral; and account, privacy, deletion, accessibility, and stated performance budgets meet their gates. No unlisted engagement, social, or caretaker feature is part of the acceptance bar.
