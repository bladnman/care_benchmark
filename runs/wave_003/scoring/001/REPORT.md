## 3. Diagnostic patterns

- **Affective vs functional.** Functional architecture survived well where the plan was explicit about invariants (S7, S8, F16, F36), but functional precision around presence (F1/F13) leaked because the reconstruction kept the event rule without the laxer-signal failure rationale.
- **Weight-3 vs weight-2.** High-weight whys did better overall because many were repeated through architecture and risk sections, but several multi-layer whys became partial when B recovered implementation and omitted downstream consequence (F17, F18, F20, F27, F30).
- **System-level vs feature-level.** System philosophy survived much better than feature-level rationale. S-level fidelity is high because the plan made architectural principles visible; feature fidelity drops where B listed many mechanisms but did not reconstruct the underlying why.
- **Multi-layer recovery patterns.** Primary implementation causes survived most often. Secondary contributor and downstream consequence layers were the common leaks, especially where the gold why described an emotional or product-category failure mode.
- **Subdomain patterns.** Audio, accessibility, performance, and identity/privacy had strong recovery. Presence accounting, social/visit semantics, notebook/read-only semantics, and bird relationship identity had weaker feature-level recovery.
- **Evidence-bound effects.** Several plausible v1-style recoveries were denied because the reconstruction evidence was rule-only: F5, F6, F8, F11, F23, F29, F31, F32, F33, F38. F34 and F35 were explicit NOT RECOVERABLE rows.

What the failure shape suggests: the plan is unusually strong at preserving executable constraints, but the blind reconstruction compresses many per-feature rationales into implementation summaries. The benchmark is therefore discriminating mostly at the "why behind the rule" layer, which is the intended v06 headroom.

## 4. Recommendations for v2 hardening

- Add more targeted feature-level whys for relationship-protection rules, not just implementation invariants. This run shows that strong plans can preserve social/privacy/notebook rules while losing why they protect the user's relationship with the birds.
- Keep multi-layer whys for high-value functional invariants, but make the downstream-consequence layer concrete enough to resist summary. F17/F18/F20 showed good rule survival with dropped failure-mode detail.
- Add a small calibration appendix for presence/accounting whys in v2. F1 and F13 were captured in the plan, but the scorer had to deny recovery because the reconstruction did not retain the laxer-signal corruption rationale.
- Preserve the evidence-bound operator. It exposed the difference between mechanism recovery and why recovery without punishing the candidate for honest NOT RECOVERABLE statements.
- Consider tightening report template language around `plan_grounding` for rule-only rows, so future scorers consistently distinguish rule evidence from rationale grounding.

## 5. Methodology caveats

- **Fresh-context fidelity.** The prompt states fresh context and the reconstruction file is frozen. I saw no contamination signs in the audit, so the safeguard appears to hold.
- **Single-run limitation.** This is one candidate and one reconstruction. No variance signal is available from this slot alone.
- **Borderline capture calls.** Feature 7 was counted captured by distributed definitions rather than a literal glossary. Feature 87 was counted not captured because the plan did not explicitly include a privacy-policy link in settings. This changes planning quality by less than one percentage point.
- **System cross-cutting.** S4 and S6 were the main subjective calls: the PLAN preserved them cross-cuttingly, but the reconstruction did not clearly identify them as system-level principles, so they scored partial.
- **Confabulation cases.** I counted no ungrounded reconstruction assertions. The reconstruction reads plan-derived; some high-salience phrases were quoted or closely paraphrased from PLAN.
- **Evidence-bound denials.** The main denials are mechanism-only rows: F5, F6, F8, F11, F23, F29, F31, F32, F33, F38.
- **Operational compromise.** `TIMING.json` supplied phase 1 and phase 2A timing for run 001 only; phase 2B timing was not present, so it was omitted rather than fabricated.
