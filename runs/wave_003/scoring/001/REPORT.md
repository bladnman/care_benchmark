## 3. Diagnostic patterns

- **Affective vs functional.** Functional recovery was slightly stronger (40.0/54.0 = 74.1%) than affective recovery (71.0/98.0 = 72.4%). Functional boundaries like S7, S8, F17, F18, F20, and F36 survived well. Affective exception whys such as F29, F33, and F39 often collapsed into rules.
- **Weight-3 vs weight-2.** Weight-3 whys recovered 80.0/108.0 = 74.1%; weight-2 whys recovered 31.0/44.0 = 70.5%. High-weight whys did survive slightly better, but many were partial because downstream-consequence layers were omitted.
- **System-level vs feature-level.** System-level fidelity was high at 89.3%, while feature-level fidelity was 69.4%. The planner encoded broad architecture and product philosophy more successfully than fine-grained relationship rationales.
- **Multi-layer recovery patterns.** Primary causes usually survived. The most common dropped layer was downstream consequence: F1/F13 did not recover silent population-wide drift corruption; F3 missed the absence-return relationship consequence; F31 missed retroactive identity collapse; F40 missed screen-reader queue overwhelm.
- **Subdomain patterns.** Server simulation, privacy, audio, and performance were strong. Social/share surfaces and account lifecycle surfaces were weaker: F23, F34, F35, and F39 became implementation rules without the product-relationship why.
- **Evidence-bound effects.** Several apparent recoveries were denied because the reconstruction only named the mechanism: F19 matter-of-fact errors, F23 no leaderboards, F29 starter birds, F33 notebook read-only, F34 export, F35 deletion, and F39 actual aviary.

What this suggests: the plan is excellent as an executable build plan, but it compresses some non-obvious affective rationales into constraints. The reconstruction then faithfully reproduced the constraints, not always the intent behind them.

## 4. Recommendations for v2 hardening

- Add more targeted feature whys around product-relationship exceptions, especially places where a strong plan will likely preserve the rule but lose the rationale: export, deletion, read-only logs, starter choices, and social sharing.
- Keep the v06 evidence-bound ledger. It distinguishes "implemented the rule" from "encoded why this rule matters," which was the main signal in this run.
- Consider asking phase-2A reconstructors to cite plan locations for each recovered why. That would make partial-layer scoring less subjective without exposing gold IDs.
- Clarify the treatment of broad system principles applied to feature-level exceptions. F10 and F22 show that a global "notice, never announce" rule can make capture likely while still leaving feature-specific why recovery ambiguous.
- Retain the 3-feature cross-cutting bar for system whys, but document whether per-feature reconstruction evidence may be used when the system-level section is compressed.

## 5. Methodology caveats

- **Fresh-context fidelity.** The validity audit found no significant contamination signs; reconstruction reads plan-derived.
- **Single-run-at-temperature limitation.** This is one sample only; no variance signal is available inside this slot.
- **Borderline capture calls.** I leaned inclusive on F10's anchor feature (#37), top-bar contents (#64), and visits default off (#90). Those calls affected planning quality by at most 2.5 points.
- **System-level cross-cutting.** S4 was the hardest system call: the plan preserved restraint across several surfaces, but the reconstruction did not name it in the system section, so it scored partial.
- **Confabulation cases.** No scored whys were marked ungrounded reconstruction; the reconstruction generally stayed within the plan.
- **Evidence-bound denials.** Rule-only recoveries were counted as capture but not why recovery for F10, F19, F23, F29, F33, F34, F35, and F39.
- **Operational compromise.** TIMING.json supplied phase 1 and phase 2A timings only; phase 2B timing was unavailable in this fresh scoring context.
